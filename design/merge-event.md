# 二合活动｜限时二合系统

> 完美世界｜系统策划实习生｜2026.07—2026.08
>
> 项目是一款面向欧美市场的卡通二合手游，核心循环为获取棋子、合成、完成订单并推进活动进度。

## 项目背景

限时活动通过订单产出代币与棋子，再由合成推进积分、阶段、通行证和图鉴，为玩家提供主线订单之外的短期目标。

我负责活动需求、玩家分层、棋子权重、订单 / Token、积分 / 通行证 / 图鉴与异常补发。设计时同时考虑产出、订单与棋盘空间：产出节奏决定玩家能做什么，订单决定目标，空间决定玩家需要做的取舍。

## 一、我怎么理解二合

| 层级 | 玩家在做什么 | 设计真正控制什么 | 需要控制的风险 |
|-|-|-|-|
| 生成器 | 消耗体力，获得代币或基础棋子 | 每日可操作次数、产出类别、恢复节奏 | 产出与目标脱节，或产出不足导致停滞 |
| 物品链 | 同级合成，逐步升阶 | 合成步数、所需空间、随机偏差 | 链条过长、订单过深、低阶物品占用棋盘 |
| 订单 | 交付指定棋子，获得积分或资源 | 需求与产出的匹配、短期目标密度 | 订单要求超出当前产出，玩家只能等待 |
| 阶段 | 解锁新区域、新棋子、新剧情 | 中期目标、内容节奏、难度变化 | 只有数值增长，缺少新的决策 |
| 奖励与商业 | 通行证、礼包、图鉴、纪念物 | 免费与付费节奏、过程奖励与最终收口 | 多个系统争用同一种价值，或奖励断档 |

核心循环可以写成：

**体力 → 生成器 → 基础棋子 → 合成 → 订单 → 活动积分/代币 → 阶段与通行证 → 新棋子/新目标 → 再生成**

循环的每一段都要回到下一轮目标，玩家的每一次操作才有意义。

## 二、项目目标与范围

项目在已有活动框架上实现限时二合，目标包括：

1. 复用既有 Reward / Shop / Popup 等能力，控制开发与美术成本；
2. 提供主线订单之外的短期追求，提升活动参与与活跃时长；
3. 用剧情、阶段、通行证和图鉴承接不同时间尺度的目标；
4. 把主题、棋子序列、棋盘结构和奖励沉淀为可复用的活动框架。

落地范围覆盖通行证、积分、无限奖励、进度、剧情、图鉴、纪念物等子系统。项目复用大部分既有配置表，仅新增少量活动专用表，并按玩家分层与棋子权重配置内容，参与从活动规则、控制流与状态定义，到配置字段、表现需求、异常补偿和测试验收的完整链路。

## 三、我负责什么

### 1. 系统与规则

- 定义"玩—得—换—再玩"的闭环：订单积分与 Token 的产出、消费与结算时机。
- 梳理活动开始、进行、结束、奖励补发和异常退出等状态。
- 把剧情、阶段、通行证、图鉴和纪念物接入同一套进度，保持各系统目标一致。
- 明确配置表、程序调用、UI 表现和前后端字段之间的边界。

### 2. 差异化设计

在基础二合上增加 Chess & Board 方向的多倍合成、棋子放置、棋盘障碍、溢出和棋盘暂存：

- **多倍合成**提高单次操作收益，同时按产出倍率、消耗与订单深度同步校准，保持物品链稳定。
- **障碍与棋盘暂存**用于调节空间压力，让整理棋盘成为有成本的决策。
- **剧情三选一**提供轻量决策与情绪价值，选择结果与核心资源保持关联。
- **通行证保留上次停留等级**，降低跨天回流成本；免费与付费奖励领取完毕后，对应抽奖道具同步耗尽，保持资源闭环。

### 3. 竞品、表现与协作

- 用模拟器、截图、录屏和视频剪辑拆解竞品的美术、机制、奖励和交互。
- 用 Codex 编写图像识别脚本，辅助测试与素材检查。
- 拆解入口 Icon、预告、开启、完成、主界面、玩法说明、礼包、Popup、本地化与美术需求，与程序、美术、QA 对齐交付。

**协作接口：**作为系统设计接口，对接 PM、战斗策划、系统策划、程序、美术和 QA；同步活动流程、订单与积分规则、配置字段、前后端边界、Icon / UI / 动效、本地化、排期风险和验收口径，并把会议结论转成文档与行动项。

### 4. 经济与数值

- 积分随棋子等级按曲线增长，再用一个膨胀系数统一控制积分规模，调整活动总量时不需要改动等级结构。
- 订单需求和棋子权重按玩家进度、付费情况与游玩时长分层，订单要求与当前产出保持匹配。
- 高等级合成附带额外产出，主序列和副序列分开配置，用来控制活动后期的奖励密度。
- 用输入输出衡算核对棋子、金币和体力的产出与消耗，确定宝箱、任务和商店各自承担的奖励份额。

## 四、关键设计判断

### 竞品参考的是约束关系

竞品真正值得参考的是它如何平衡以下参数：

- 玩家一天能生成多少次；
- 从基础棋子到订单目标需要多少步；
- 棋盘能容纳多少个未完成分支；
- 订单需求偏向哪一阶物品；
- 阶段奖励在什么时候给，能否形成下一次操作动机。

这些参数决定体验，界面形式在此之后才确定。

### 棋盘空间是核心资源

二合的难度同时来自订单数值与空间。低阶棋子积压会限制继续生成，因此障碍、溢出和暂存共同调节三件事：

**继续合成的机会 ↔ 整理棋盘的成本 ↔ 付费或等待的动机**

## 五、验证与结果

- 用 SVN / Unity + GM 覆盖活动开启、状态切换、数值配置、订单结算、奖励发放和异常场景。
- 按"控制流—配置—表现—异常"四层检查，覆盖正常流程之外的边界情况。
- 核对奖励发放、补发和领取状态，提交并跟进 Bug。
- 与程序、美术、QA 对齐入口、UI、本地化和配置字段，保证方案可以落地。

最终形成可替换主题、棋子、棋盘和奖励的活动框架，以及流程、配置与异常场景的验收基线。

## 六、后续验收指标

1. **首次体验：**首次合成、首次订单、首次棋盘满、首次阶段完成分别发生在第几分钟。
2. **节奏：**每日生成次数、订单完成时长、阶段完成天数和通行证进度是否与活动周期匹配。
3. **空间压力：**棋盘占用峰值、溢出次数、暂存使用率和因满盘退出的比例。
4. **随机偏差：**用固定种子和批量模拟检查连续未出目标物品的尾部情况。
5. **商业边界：**付费用于缩短等待，核心决策仍由玩家完成；免费玩家同样拥有完整的阶段目标。

## 复盘

- 把合成与收集类玩法拆成生成、转换、需求、空间和奖励五个约束。
- 先跑通最小闭环，再扩充内容；先验证产出与需求闭合，再讨论美术与包装。
- 用状态机描述活动生命周期，用配置表描述可变内容，用日志验证实际到账。
- 竞品功能需要先回答用户价值与自身优势，再进入设计。
