# 二合活动｜限时二合系统

> 完美世界｜系统策划实习生｜2026.07—2026.08
>
> 项目是一款面向欧美市场的卡通二合手游，核心循环为获取棋子、合成、完成订单并推进活动进度。公开版不包含内部 ID、真实权重和原始配置。

## 项目背景

限时活动里，玩家用订单拿到代币和棋子，再通过合成推进积分、阶段、通行证和图鉴。它要补的是主线订单之外的短期目标。

我负责活动需求、玩家分层、棋子权重、订单 / Token、积分 / 通行证 / 图鉴和异常补发。做这类活动时，产出、订单和棋盘空间必须一起看：产出多了棋盘会塞满，订单奖励给多了，后面的目标又失去意义。

## 一、我怎么理解二合

| 层级 | 玩家在做什么 | 设计真正控制什么 | 需要控制的风险 |
|-|-|-|-|
| 生成器 | 消耗体力，获得代币或基础棋子 | 每日可操作次数、产出类别、恢复节奏 | 产出与目标脱节，或产出不足导致停滞 |
| 物品链 | 同级合成，逐步升阶 | 合成步数、所需空间、随机偏差 | 链条过长、订单过深、低阶物品占用棋盘 |
| 订单 | 交付指定棋子，获得积分或资源 | 需求与产出的匹配、短期目标密度 | 订单要求超出当前产出，玩家只能等待 |
| 阶段 | 解锁新区域、新棋子、新剧情 | 中期目标、内容节奏、难度变化 | 只有数值增长，缺少新的决策 |
| 奖励与商业 | 通行证、礼包、图鉴、纪念物 | 免费与付费节奏、过程奖励与最终收口 | 多个系统争用同一种价值，或奖励断档 |

核心循环可以写成：

**体力 → 生成器 → 基础棋子 → 合成 → 订单 → 活动积分/代币 → 阶段与通行证 → 新棋子/新目标 → 再生成**

其中任何一段回不到下一轮目标，玩家就会觉得自己只是在重复拖拽。

## 二、项目目标与范围

项目是在已有活动框架上做限时二合，不需要从零重写一套合成系统。我的目标有四个：

- 复用既有 Reward / Shop / Popup 等能力，把开发和美术成本压住；
- 给玩家主线订单之外的短期追求；
- 用剧情、阶段、通行证和图鉴分别接住不同时间尺度的目标；
- 把主题、棋子序列、棋盘结构和奖励做成下一次活动能直接复用的框架。

落地范围包括通行证、积分、无限奖励、进度、剧情、图鉴和纪念物。配置表大部分复用，只新增少量活动专用表；内容按玩家分层和棋子权重配置。我参与的链路从活动规则、控制流和状态定义，一直到配置字段、表现需求、异常补偿和测试验收。

## 三、我负责什么

### 1. 系统与规则

- 定义“玩—得—换—再玩”的闭环：订单积分与 Token 怎么产出、怎么消费、什么时候结算。
- 梳理活动开始、进行、结束、奖励补发和异常退出的状态。
- 把剧情、阶段、通行证、图鉴和纪念物接进同一套进度，避免各做一套独立计数。
- 明确配置表、程序调用、UI 表现和前后端字段之间的边界。

### 2. 差异化设计

在基础二合上，我加了 Chess & Board 方向的多倍合成、棋子放置、棋盘障碍、溢出和暂存。多倍合成提高单次操作收益，但产出倍率、消耗和订单深度要一起校准，否则会把原来的物品链打穿。障碍和暂存用来调节空间压力：太宽松，整理就没有意义；太严格，玩家会被迫频繁付费或退出。剧情三选一提供轻量决策和情绪价值，选择结果也会落到核心资源上。通行证保留上次停留的等级，降低跨天回流的成本；免费与付费奖励领完后，对应的抽奖道具刚好用完。

### 3. 竞品、表现与协作

- 用模拟器、截图和录屏拆竞品的美术、机制、奖励和交互。
- 用 Codex 写图像识别脚本，辅助测试和素材检查。
- 拆入口 Icon、预告、开启、完成、主界面、玩法说明、礼包、Popup、本地化和美术需求，与程序、美术、QA 对齐交付。

**协作接口：**作为系统设计接口，对接 PM、战斗策划、系统策划、程序、美术和 QA；同步活动流程、订单与积分规则、配置字段、前后端边界、Icon / UI / 动效、本地化、排期风险和验收口径，并把会议结论转成文档与行动项。

### 4. 经济与数值

- 积分随棋子等级按曲线增长，再用膨胀系数控制整体积分规模。
- 订单需求和棋子权重按玩家进度分层，保证订单要求和当前产出匹配。
- 用输入输出衡算核对棋子、金币和体力的产出与消耗，确定宝箱、任务和商店各自承担的价值。
- 棋子选中、拖动、合成和订单提交的反馈规则也一并定义，保证玩家看得懂操作结果。

### 5. 配置逻辑

- **棋子与积分：**ActMergeConfig 按棋子 ID 配置积分，结算时除以膨胀系数并四舍五入，这样调整整体积分规模时不需要改动等级结构。
- **合成产出：**ActMergeStageConfig 按棋盘、序列和等级定义棋子；OutputType 区分"合成时自动产出"和"点击产出（宝箱）"，Additions 配置额外产出的棋子，用来控制高级合成时的奖励密度，主序列和副序列可以分开配置。
- **开放与解锁：**ActivityConfig 用 month / week / day 配置功能的循环开放与持续天数，LevelConfig 用解锁等级控制各功能的出现顺序；活动自身再按预告、开启、进行、完成、结束拆分状态，未完成的情况走派生流程。
- **引用一致性：**棋子 ID 在积分、产出、订单和展示表中保持一致，调整棋子结构时只需要改配置层。

## 四、关键设计判断

### 竞品真正值得参考的是约束关系

竞品的界面只能说明“它现在有效”，不能说明我们的用户、体力节奏、物品链和商业化能不能接住。所以我拆的是这些参数：玩家一天能生成多少次；从基础棋子到订单目标要几步；棋盘能容纳多少未完成分支；订单需求偏向哪一阶物品；阶段奖励什么时候给，能不能形成下一次操作的动机。这些参数一变，同一个 UI 会得到完全不同的体验。

### 棋盘空间是核心资源

二合的难度不只来自订单数值，也来自空间。低阶棋子积压后玩家无法继续生成，等于隐性卡关。所以障碍、溢出和暂存不是附属功能，它们在调节三件事：

**继续合成的机会 ↔ 整理棋盘的成本 ↔ 付费或等待的动机**

## 五、验证与结果

- 用 SVN / Unity + GM 覆盖活动开启、状态切换、数值配置、订单结算、奖励发放和异常场景。
- 按“控制流—配置—表现—异常”四层检查，而不是只测正常路径。
- 核对奖励发放、补发和领取状态，提交并跟进 Bug。
- 与程序、美术、QA 对齐入口、UI、本地化和配置字段，减少文档写完后无法落地的返工。

最终形成可替换主题、棋子、棋盘和奖励的活动框架，以及流程、配置与异常场景的验收基线。

## 六、后续验收指标

- **首次体验：**首次合成、首次订单、首次棋盘满、首次阶段完成分别发生在第几分钟。
- **节奏：**每日生成次数、订单完成时长、阶段完成天数和通行证进度是否与活动周期匹配。
- **空间压力：**棋盘占用峰值、溢出次数、暂存使用率和因满盘退出的比例。
- **随机偏差：**用固定种子和批量模拟检查连续未出目标物品的尾部情况。
- **商业边界：**付费用于缩短等待，核心决策仍由玩家完成；免费玩家同样拥有完整的阶段目标。

## 复盘

- 把合成与收集类玩法拆成生成、转换、需求、空间和奖励五个约束。
- 先跑通最小闭环，再扩内容；先验证产出与需求闭合，再讨论美术和包装。
- 用状态机描述活动生命周期，用配置表描述可变内容，用日志验证实际到账。
- 竞品功能需要先回答用户价值与自身优势，再进入设计。
