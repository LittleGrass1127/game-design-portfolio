# 青蛙战斗｜强数值活动的战斗与奖励闭环

> 项目案例：《无限暖暖》3.0 活动战斗数值（项目代号「青蛙战斗」，公开版脱敏）。本文只写设计目标、判断过程、验证方法与相对结果，不包含内部 ID、原始配置、具体怪物表、未公开奖励路径与服务器数据。

## 一句话

这不是一张“把怪物血量填到能过”的表，而是一条从活动总消耗、养成上限、技能收益、怪物强度到奖励回流的完整数值链。

## 一、设计目标

新版本活动需要验证一件事：**强数值玩法能否被现有用户群接受，并在不破坏角色、探索和情绪陪伴体验的前提下扩大覆盖。**

因此活动战斗同时承担四个目标：

1. 给玩家一个清晰的成长验证场景；
2. 让活动商店、升级材料、技能解锁和抽卡形成同一条消耗路径；
3. 让不同投入层级的玩家都能看见下一步，而不是只服务满养成用户；
4. 为后续版本判断“强数值活动”是否值得继续投入。

活动按约 20 天周期、30 级成长和 12 个怪物难度展开；怪物不是独立拍数值，而是从玩家在对应阶段能达到的等级、技能与材料存量反推。

## 二、我负责什么

- **活动战斗数值：**玩家与怪物属性、普通怪与 Boss 的生命 / 攻击 / 攻速、预期战斗时长。
- **成长与技能：**升级材料消耗、每级属性成长、20 个技能、3 个槽位、技能解锁和强化节奏。
- **奖励与消耗：**商店分层、每日限购、活动货币产出与消耗、首杀 / 复刷 / 任务奖励的拆分。
- **验证：**Excel 配表、Codex 批量模拟、UE 实机、GM/Lua 构造场景、服务器日志核对。

## 三、关键难点

### 1. 怪物强度不能先拍，再让玩家追

如果先写一个“看起来很厉害”的 Boss，再倒推玩家要练到多少级，很容易出现前期断层、后期无事可做。我的顺序相反：

1. 先拆活动周期内玩家能达到的等级、技能和材料上限；
2. 用“同阶段玩家打同阶段怪”建立基准；
3. 用有效生命 / DPS 和 TTK 反推怪物血量、攻击与攻速；
4. 用容错次数检查玩家能吃几次技能、打多久、需要几轮循环；
5. 再把技能成长放进时间轴，检查后期是“数值变强”还是“操作变简单”。

### 2. 攻速调整后，不能把全部伤害简单除以 1.65

攻速公式调整后，同一属性等级下的出手频率提高约 1.5–1.71 倍。直接按一个固定倍率削全部技能，会同时破坏直伤、持续伤害、控制、护盾和吸血的相对价值。

我按 31 个属性等级 × 3 种战斗时长 × 3 个技能槽位展开 **279 个战斗情形**：

- 旧频率下共释放 2,071 次；
- 新频率下共释放 3,417 次；
- 汇总约 **1.6499 倍**，但这是等权参考，不是每个技能固定乘 1.65。

最终分别处理：

- 只调整灼烧、护盾、眩晕、吸血相关技能的基础直伤；
- 吸血从 80% 调整为 50%，护盾保留 2%；
- 灼烧继续按独立 2 秒跳伤、10 层上限和战斗结束截断处理；
- 不把出手间隔当作跳伤间隔；
- 直伤保留 1 个百分点精度，高数值按 5 个百分点档向下取整；
- 没有为了“统一”强行削弱已经通过离散检查的技能。

### 3. 旧技能跳关、新技能没有使用理由

技能的乘区、覆盖率和解锁顺序如果不统一，会出现两个问题：旧技能在新等级段直接跳关，新技能虽然数值更高但没有上场理由。

我的处理是把 20 个技能、3 个槽位按乘区和覆盖率等效，灼烧叠层设衰减上限，新技能按解锁顺序递增系数；不是简单把新技能做得比旧技能强。

### 4. 配置正确不等于游戏实际加载正确

跑测中发现攻速与旧缓存 / 技能数量绑定不一致。我的处理是先用系数兜底，保证当前版本可验证，再提出拆分玩家和怪物逻辑的需求，避免把缓存问题伪装成数值问题。

## 四、奖励闭环

3.0 Boss 奖励拆成三路：

| 奖励入口 | 内容 | 目的 |
|---|---|---|
| 任务一次性 | 4 件服装图纸 | 保证主线参与和收藏价值 |
| 首杀 | 2 个养成道具 | 鼓励首次挑战，不鼓励无限刷 |
| 复刷 | 基础材料 | 维持可重复游玩，不冲击首杀价值 |

按 UID 核对任务、首杀、复刷三个入口，避免串包。奖励不是“越多越好”，而是让每个入口承担不同的玩家动机。

## 五、验证与结果

### 批量模拟

- 覆盖 1–31 级、3 种战斗时长、3 个槽位，共 279 个战斗情形；
- 同时看平均、中位数和尾部，不只看“平均能过”；
- 对技能释放次数、有效生命、控制占比和伤害窗口做对比，而不是只看面板 DPS。

### 关卡与路线验证

- 12 关 Boss 按解锁顺序逐关验证；
- 最终配置和当前计划成长装配下，**324 条合法垃圾话路径全部获胜**；
- 无垃圾话、最佳选择，以及假设 0.25 / 0.5 / 1 秒统一命中延迟时也能通过；
- 这些是规则和配置可达性验证，不是真人胜率，也不代表所有配队都能过。

### GM / Lua 实测

用 GM 和 Lua 构造测试场景：

- 改任务标记、资源、时间、功能解锁和目标状态；
- 直接进入指定战斗、升级指定技能、修改青蛙属性；
- 批量发奖、推进任务、循环构造样本；
- 以服务器日志为准核对掉落 ID、奖励到账和任务状态；
- 脚本按 ID 做重复保护，失败先查日志，不整批重发。

**请求发出不算成功，只有日志和账户结果一致才算验收。**

## 六、成果与边界

- 形成从活动总消耗、成长曲线、技能收益、怪物强度到奖励回流的完整数值链。
- 12 关 Boss 按解锁顺序完成验证，首关通关、倍率逐档、日志到账作为验收口径。
- 攻速改版后没有用“一刀切除以 1.65”掩盖差异，而是分别重标直伤、持续伤害、控制、护盾和吸血。
- 对配置缓存、技能数量和实际加载不一致的问题，先兜底、再提需求拆分逻辑。

边界：以上是项目内数值方案与测试方法，不代表线上留存、收入或玩家满意度；具体配置、真实 ID、怪物表、奖励路径和服务器数据不在公开作品集中展示。

## 七、可迁移的方法

1. 先定玩家能到哪，再定怪物多强。
2. 先拆有效生命、DPS、TTK、覆盖率和乘区，再讨论单个技能。
3. 任何全局倍率变化，都要按机制分别重标，不做一刀切。
4. 模拟负责暴露分布和边界，实机负责验证加载和表现，日志负责确认到账。
5. AI 可以批量生成模拟和测试脚本，但目标、取舍和验收必须由人负责。
