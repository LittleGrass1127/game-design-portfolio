# 面试复盘与原创设计｜青蛙、二合、暗黑4、原神

> 材料来源：个人面试记录与项目复盘笔记。本文区分“项目事实”“面试原回答”“复盘后的更好回答”和“原创设计提案”。

## 先看结论

我在青蛙和二合项目里真正做的，不是把竞品功能搬进配置表，而是把模糊目标翻译成一套可计算、可落地、可验证的关系：

- 青蛙：**商店限购 → 材料与时间 → 等级 → 战力 → Boss 难度 → 战斗与奖励反馈**
- 二合：**体力/订单 → Token/棋子 → 合成 → 积分/阶段 → 通行证/图鉴 → 再生成**
- 新职业/角色：先找现有产品里缺失的玩家决策，再设计核心机制、资源循环、构筑轴、验证指标和失败边界。

# 一、青蛙战斗｜面试到底问了什么

## 1. 项目事实

- 版本：3.1 活动战斗数值，同时负责 3.0 怪物奖励配置。
- 顶层约束：活动货币总消耗上限、约三周的活动周期、有限的等级上限、12 个怪物难度。
- 我负责：活动商店限购、材料消耗、玩家等级与属性、技能收益、怪物攻击/生命/攻速、战斗时长、奖励拆分。
- 设计链路：用商店限购控制材料投放和活动节奏；由材料与等级推出时间—战力；再用有效生命、DPS、TTK、技能覆盖率与难度系数反推怪物。
- 验证：属性等级 × 战斗时长 × 技能槽位，共 279 个战斗情形。
- 攻速改版：同属性下频率明显提高且各等级段幅度不同，不能把全部伤害统一除以一个倍率，需要分别重标直伤、持续伤害、控制、护盾和吸血。
- 本地复盘的测试基线：普通玩家、最差玩家、技能平衡用例全部通过，12 关 324/324，公式错误 0；这些是测试口径，不等于线上留存或收入。

## 2. 面试官问：等级上限是怎么来的？

**我的原始回答：**

> 我的预设是升满需要的材料比活动期内的发放量更多；玩家不需要满级，中等战力就能通关。这样能形成比较合适的追赶空间。等级也和 12 个怪物的难度曲线、取整和活动货币总消耗相互约束。

**复盘后更有结构的回答：**

1. **时间约束：**等级上限略高于活动期内能稳定达到的等级，让玩家在活动结束前仍有可见的成长尾段，而不是前半段就把养成打满。
2. **通关约束：**目标是中等战力可以通关，剩余空间留给不同投入、操作和阵容差异，不用满级才配体验完整内容。
3. **怪物约束：**12 个怪物需要足够的等级台阶区分难度；等级太少会让玩家跳级、技能组合越级，等级太多又会让材料发放和整数取整失真。
4. **经济约束：**材料、货币、商店限购和升级消耗必须同时满足整数与总量约束，等级上限是这些关系共同收敛后的结果，不是单独拍出来的数字。

## 3. 面试官问：如果等级调高或调低，会影响什么？

**原始回答的核心：**

- 等级拉得太高：材料发放、战力跨级和怪物台阶会错位，玩家可能从 2 级直接跳到 4 级、6 级，3 级和 5 级的体验没有被利用。
- 等级太少：无法用足够多的战力台阶区分 12 个怪物，难度曲线会变粗，也更容易被技能组合跳关。

**复盘后的判断：**

> 等级不是独立的成长数字，而是“时间、材料、战力、怪物、技能”五个系统的共同刻度。调整等级实际上是在改变玩家看到成长反馈的频率、Boss 卡点的密度和技能升级的窗口。

## 4. 面试官问：最难的问题是什么？

**我的原始回答：**

> 技能之间有平衡和逻辑问题。新技能需要比旧技能更有使用理由，但不能让旧技能完全失效。我先计算每个技能独立词条和乘区，再把覆盖率、灼烧溢出、护盾、吸血折算成等效收益，最后乘技能解锁系数，让技能随进度变强。

**复盘后可以更强的回答：**

- 先区分问题层级：是数值系数不对、机制难以反制，还是技能解锁后让旧技能失去选择。
- 技术服务数值：灼烧按独立跳伤、叠层上限和结束截断计算；护盾和吸血要转成有效生命，而不是直接按面板百分比比较。
- 最后做场景矩阵：不同等级、战斗时长和技能槽位组合，避免只看一张 DPS 排名。
- 已知边界：模拟不等于真人操作，护盾/吸血是收益上界，配置加载和缓存问题也要与数值问题分开。

## 5. 如果面试官问“为什么不是抄竞品？”

**回答：**

> 竞品只能证明类似需求存在，不能证明它适合我们的用户。换装开放世界用户更看重角色、探索和陪伴，如果直接把硬核战斗照搬进来，会把不想高投入的用户排除。因此我把强数值做成“可退出”的活动验证：商店限购控制节奏，Boss 验证玩家当前战力，奖励回流承接继续参与，而不是用竞品数值硬套。

# 二、二合活动｜面试与项目实际

## 1. 项目事实

项目目标是在现有 Reward / Shop / Popup 框架上做一个可复用的限时二合活动，补齐主线订单外的短期追求，并用剧情、阶段、通行证、积分、图鉴承接短中长期目标。

- 复用大部分既有配置表，只新增少量活动专用表。
- 主循环：**体力/订单 → Token/棋子 → 合成 → 积分/阶段/通行证/图鉴 → 再生成**。
- 玩家分组和棋子权重决定产出；订单需求决定短期目标；棋盘空间、障碍、溢出和暂存决定操作压力。
- 差异化：Chess & Board 多倍合成、棋子放置、障碍、溢出、棋盘暂存、剧情三选一、通行证保留上次等级。
- 验证：Unity/SVN、GM、状态切换、数值配置、奖励发放和异常场景；按“控制流—配置—表现—异常”分层检查。

## 2. 面试官问：二合的积分功能怎么配？

**我的原始回答：**

> 先引用已有玩家分组，配置每级所需积分与最大积分；到达最大等级后，进入无限积分阶段，配置每次消耗积分和固定奖励。奖励字段再引用 Reward 表，表中只存奖励段或引用，具体 Icon、数量和类型在 Reward 表里配。

**复盘后的结构：**

1. **活动层：**读取活动开关、开始时间和结束时间。
2. **玩家层：**按玩家分组读取订单/积分区间和 Token 数量。
3. **进度层：**配置每级积分门槛、奖励引用、无限阶段消耗。
4. **奖励层：**主表只引用 Reward，具体奖励单独维护。
5. **表现层：**积分进度、奖励弹窗、动画和本地化分开配置。

## 3. 面试官问：哪些字段放客户端，哪些放服务器？

**我的原始回答：**

> 重要货币、奖励发放、战斗数值和影响平衡的规则需要本地和服务器都校验；图片和纯展示资源可以放本地；服务器时间要用于活动倒计时和结算；提前结束、活动结束未领取、支付补单等需要服务器兜底。

**复盘后的原则：**

- 客户端：展示、输入、即时反馈、可替换的本地资源和预览。
- 服务器：货币、奖励、活动时间、购买、领取、补偿和防篡改。
- 双端：涉及数值平衡、奖励引用和活动状态的关键字段；客户端负责体验，服务器负责权威结果。
- 验收：请求成功不算成功，必须核对服务器结果、奖励到账和状态变化。

## 4. 面试官问：为什么做二合，为什么不是直接复制？

**回答：**

> 竞品验证的是“这个需求成立”，不是提供一套可以直接复制的棋盘和数值。我们的项目已有 Reward/Shop/Popup 框架，开发成本要求复用，所以真正要设计的是约束关系：玩家一天能生成多少次、棋子权重如何产出、订单需要多深、棋盘能承受多少低阶物品、阶段和通行证在什么时候给目标。直接复制 UI 会得到不同的体验；复制约束并重新求解，才是设计。

## 5. 项目的巧思与失败边界

- 棋盘空间是隐藏资源：障碍、溢出和暂存不是附属功能，而是在调节继续合成的机会、整理成本和付费/等待动机。
- 多倍合成提高单次收益，但必须同步控制产出倍率、订单膨胀和消耗，否则会打穿原物品链。
- 剧情三选一提供轻量决策和情绪价值，但不能和核心资源脱节。
- 通行证保留上次等级降低跨天回流成本；免费/付费奖励领完后对应抽奖道具刚好耗尽，避免无效货币溢出。
- 不足：缺少线上数据验证，棋盘压力和多倍合成仍需长测；下一版前置首合、首单、满盘、阶段完成等指标和 A/B。

# 三、从两个项目抽象出的设计方法

1. **先定义玩家要经历的体验**：成长、选择、压力、收集、陪伴还是爽快？
2. **再定义玩家反复做什么**：核心动词、操作循环、短期目标和长期目标。
3. **找控制变量**：资源产出、消耗、权重、时间、空间、概率、操作、社交。
4. **把变量变成关系**：不是问攻击力是多少，而是问输出/生命、产出/消耗、收益/成本、风险/回报。
5. **先做最小闭环**：小样本跑通，再扩内容、表量、UI、本地化和异常。
6. **用场景矩阵验证**：正常、极端、低投入、高投入、尾部随机和异常加载。
7. **写清边界**：哪些是模拟，哪些是实机，哪些是团队结果，哪些还没验证。

# 四、原创设计｜暗黑4新职业：罪契使

> 这是原创设计提案，不代表暴雪官方职业或项目内容。

## 1. 设计目的

暗黑4已有高资源循环、召唤、远程施法、近战连击和装备驱动等职业。新增职业不能只是“换个元素的死灵法师”，而要提供新的玩家决策。

**罪契使**的核心幻想是：把敌人造成的伤害、自己承受的风险和即将发生的爆发记在一本“罪契”上，玩家决定是现在讨债，还是把债转成防御。

## 2. 核心机制：罪印与债

- 攻击会给敌人叠加“罪印”。
- 玩家受到伤害或对带罪印目标造成伤害时，积累“债”。
- 玩家可以选择：
  - **讨债：**消耗债，立即对目标造成爆发伤害；
  - **赎罪：**消耗债，转化为护盾、减伤或控制抗性。
- 债有上限和自然衰减，不能无限存着等 Boss 窗口。

这使输出和生存共享同一个资源，玩家必须判断“现在兑现收益，还是留作容错”。

## 3. 技能与循环

基础循环：**挂罪印 → 产生债 → 选择讨债/赎罪 → 用业火强化下一轮 → 重新挂印**

- 基础技能：断罪链，近中距离挂罪印。
- 核心技能：孽火斩，消耗业火，扩大罪印。
- 资源技能：索债，按债的层数造成爆发。
- 防御技能：替罪契，把部分伤害转成债并延迟结算。
- 位移技能：幽链摆渡，拉向目标或拉开距离。
- 终极技能：七宗审判，根据债的类型触发不同效果。

## 4. 构筑轴

- **讨债爆发：**快速叠债、缩短兑现窗口，适合精英和 Boss。
- **赎罪反击：**用受伤转债、护盾和反伤，适合高压近战。
- **锁链控场：**把罪印扩散到多目标，适合刷图和大密度场景。

## 5. 装备与终局

传奇威能应改变“债如何产生、如何兑现”，而不是只加技能伤害；Unique 可以设计成“债上限提高但自然衰减加快”，让玩家主动管理风险。Paragon 节点分别强化罪印扩散、债兑现、防御转换和位移后的短窗口。

## 6. 验证指标与风险

- 指标：单体/群体击杀时间、债的平均存量、兑现频率、防御覆盖、构筑使用率、不同场景的胜率。
- 风险：债无限存导致 Boss 一波秒杀；防御转换让玩家无脑堆生存；多目标叠印导致性能或数值爆炸。
- 对策：债上限、自然衰减、Boss 阶段重置、单目标独立结算、兑现后短暂锁印。

## 7. 为什么不抄现有职业

死灵法师的循环是“资源→召唤/尸体→消耗”；罪契使的循环是“风险→记账→现在兑现还是以后兑现”。它的新意不在召唤物或技能特效，而在**进攻和防守共用一笔未来的债**。

# 五、原创设计｜原神新角色：顾霜｜留白

> 这是原创设计提案，不代表米哈游官方角色或项目内容。

## 1. 设计目的

原神已有大量后台挂元素、增伤、护盾和治疗角色。新角色不能只是“冰系后台副 C”，而要让玩家改变队伍顺序和爆发窗口。

**顾霜**是璃月的霜墨画师，用画纸记录战斗中最后一笔元素，再用冰霜把这一笔“复现”出来。

## 2. 角色定位

- 元素：冰
- 武器：法器
- 星级：五星
- 定位：后台副 C / 爆发窗口辅助
- 核心资源：霜意

## 3. 核心机制：留白与摹写

- 元素战技“落霜成笺”：给目标挂上“留白”，持续记录队伍造成的元素反应。
- 记录到的元素类型决定“摹写”的附加效果：
  - 火：提高爆发伤害；
  - 水：提供小幅持续治疗；
  - 雷：回复元素能量；
  - 冰：延长留白时间。
- 元素爆发“一纸留白”：消耗霜意，复现记录的元素，并造成一次冰元素范围伤害。
- 记录有上限、不可递归、不会复制角色技能倍率，只记录元素类型和层数。

## 4. 核心循环

**战技挂留白 → 队友触发反应 → 记录元素 → 切回顾霜 → 爆发兑现 → 为下一轮留出空窗**

这不是“按 E 后 Q 就增伤”，而是要求玩家安排队友的出手顺序，决定把哪种元素留给顾霜兑现。

## 5. 配装与队伍

- 反应队：火/水/雷队通过不同记录获得伤害、治疗或充能。
- 永冻队：通过冰记录延长控制和留白覆盖。
- 爆发队：用短窗口高倍率角色让顾霜记录后集中兑现。

## 6. 验证指标与风险

- 指标：留白覆盖率、记录成功率、爆发贡献、元素附着频率、充能需求、队伍 DPS、使用率和操作复杂度。
- 风险：记录高倍率技能导致爆发超模；多目标记录导致 AoE 爆炸；治疗/充能效果让角色变成全能辅助。
- 对策：只记录元素类型不记录原始倍率；按队伍和敌人分别设上限；治疗/充能设独立 CD；Boss 转阶段清空记录。

## 7. 为什么不是“又一个冰辅助”

她的设计核心不是加一个增伤乘区，而是让玩家规划“把哪一次反应留给谁兑现”。角色强度和操作顺序、队伍元素、爆发窗口绑定，符合原神以元素反应和切人节奏为核心的设计语言。

# 六、被质疑时怎么答

## 1. “二合难道只是抄的吗？”

> **回答骨架：**承认品类成熟，但不承认设计只是复制。竞品验证需求，我们重新求解约束。

**可以直接这样说：**

> “如果只看拖拽合成，二合当然是成熟品类，我不会说这个品类是我首创的。但项目里不能直接把竞品棋盘和数值搬过来：我们有既有的 Reward / Shop / Popup 框架、既有表复用和少量新增的成本约束，也要服务自己的用户和活动周期。我真正做的是重新定义玩家分组、棋子权重、订单需求、棋盘空间、阶段和奖励之间的关系，再增加 Chess & Board、多倍合成、障碍、溢出、暂存、剧情三选一和通行证跨级保留。判断是不是抄，不看有没有相同按钮，而看玩家的决策和系统关系有没有被重新设计。”

- **追问“这些竞品也有”：**相同功能不等于相同设计。继续讲它在我们的活动周期、玩家分层、棋子权重和奖励节奏里解决什么问题；如果删掉它会损失什么体验。
- **追问“你负责多少”：**明确自己负责系统规则、配置字段、表现需求、异常补偿和测试协同，不把美术、程序或整个产品的成果算成个人功劳。
- **追问“没有线上数据”：**不声称产品成功，只声称完成了系统实现、配置和测试覆盖；下一阶段该看首合、首单、满盘、阶段完成和通行证进度。

## 2. “青蛙玩法你只是实现了而已吗？”

> **回答骨架：**先承认玩法框架不是自己从零定的，再说明自己在框架内做了哪些设计判断。

**可以直接这样说：**

> “这个活动的主题和基础战斗框架不是我一个人从零提出来的，我负责的是数值模块和验证。但数值不是把表填满：为什么是这个周期、这个等级上限、12 个怪物，为什么中等战力可以通关，技能如何按解锁顺序变强，攻速改版后为什么不能把全部伤害统一除以一个倍率，奖励为什么拆成任务、首杀和复刷三路，这些都是会影响玩家行为和体验的设计判断。实现只是最后一步，前面是在决定玩家什么时候成长、什么时候卡住、为什么愿意继续打。”

- **证明不是纯填表：**讲时间→等级→战力→Boss 难度的链路；讲 279 个战斗情形、技能与槽位等效、场景矩阵和奖励分流。
- **证明会修改：**攻速变化后按直伤、持续伤害、控制、护盾、吸血分别重标；配置加载错位先兜底，再推动玩家与怪物逻辑拆分。
- **证明知道边界：**模拟不等于真人，护盾和吸血是收益上界，首关、倍率、日志到账只是当前验收口径，线上体验仍需继续验证。

## 3. 如果对方继续压：“那你的设计水平体现在哪里？”

1. **能把模糊目标变成关系：**不是问血量填多少，而是先问玩家在什么时间应该达到什么战力、应该打多久、能承受几次失误。
2. **能分辨问题层级：**是系数、机制、配置加载还是玩家操作的问题；不把所有问题都当成加一点数值。
3. **能让别人执行：**把规则、字段接口、状态流、表现需求和验收口径讲清楚，让程序、美术、QA 能按同一标准交付。
4. **能承认没验证的部分：**不把团队上线结果冒充个人成果，也不把“功能做完”当成“体验成立”。

## 4. 回答时的三条底线

- 不说“这个玩法是我首创的”，除非有明确证据。
- 不把团队在线数据、收入或留存写成个人结果。
- 不只说“我参与了”，要说清自己负责的模块、做出的取舍和可核验的结果。

# 七、三分钟面试讲法

> 我做青蛙战斗时，先把活动周期拆成时间—材料—等级—战力—Boss 难度，再用有效生命和 DPS 反推怪物，最后用 GM/Lua 和日志验证。  
> 做二合时，我没有照抄竞品，而是先还原生成器、棋子权重、订单、棋盘空间、阶段和奖励的关系，再在现有框架上做 Chess & Board、剧情和通行证的差异。  
> 这两个项目让我形成了同一套方法：先找玩家的决策，再设计数值关系，先跑最小闭环，最后明确哪些已经验证、哪些还没有。
