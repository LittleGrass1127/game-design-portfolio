# 二合活动｜从玩法理解到项目落地

> 项目案例：海外休闲二合活动「冬日焕彩」（作品化代称）。本文写设计判断、系统关系、配置落地和验证方法，不包含内部 ID、真实权重、未公开数值与原始配置。

## 一句话

二合不是“把三个相同物品拖到一起”，而是一套同时管理**生成效率、棋盘空间、订单需求、阶段目标和奖励回收**的资源转换系统。

## 一、我怎么理解二合

| 层级 | 玩家在做什么 | 设计真正控制什么 | 常见失败 |
|---|---|---|---|
| 生成器 | 消耗体力，获得代币或基础棋子 | 每日可操作次数、产出类别、恢复节奏 | 产出多但没有目标，或产出少导致卡死 |
| 物品链 | 同级合成，逐步升阶 | 合成步数、所需空间、随机偏差 | 链条过长、订单过深、棋盘被低阶物品塞满 |
| 订单 | 交付指定棋子，获得积分或资源 | 需求与产出的匹配、短期目标密度 | 订单要求高于当前产出，玩家只能等待 |
| 阶段 | 解锁新区域、新棋子、新剧情 | 中期目标、内容节奏、难度变化 | 只有数值增长，没有新决策 |
| 奖励与商业 | 通行证、礼包、图鉴、纪念物 | 免费与付费节奏、过程奖励与最终收口 | 多个系统抢同一种价值，或奖励断档 |

核心循环可以写成：

**体力 → 生成器 → 基础棋子 → 合成 → 订单 → 活动积分/代币 → 阶段与通行证 → 新棋子/新目标 → 再生成**

如果其中任何一段不能回到下一轮目标，玩家就会感觉自己只是在重复拖拽。

## 二、项目目标与范围

项目是在已有活动框架上做限时二合，目标不是从零重写一套合成系统，而是：

1. 用既有 Reward / Shop / Popup 等能力压住开发和美术成本；
2. 让活动具备主线订单之外的短期追求，提高参与率与活跃时长；
3. 用剧情、阶段、通行证和图鉴承接不同时间尺度的目标；
4. 把主题、棋子序列、棋盘结构和奖励做成可复用的活动框架。

落地范围包括通行证、积分、无限奖励、进度、剧情、图鉴、纪念物等多条子系统。项目复用 15 张配置表，新增 10 张表；按玩家分层和棋子权重配置内容，参与从活动规则、控制流和状态定义，到配置字段、表现需求、异常补偿和测试验收的完整链路。

## 三、我负责什么

### 1. 系统与规则

- 定义“玩—得—换—再玩”的闭环：订单积分与 Token 如何产出、如何消费、何时结算。
- 梳理活动开始、进行、结束、奖励补发和异常退出等状态。
- 把剧情、阶段、通行证、图鉴和纪念物接入同一套进度，而不是各做一套独立计数。
- 明确配置表、程序调用、UI 表现和前后端字段之间的边界。

### 2. 差异化设计

在基础二合上增加 Chess & Board 方向的多倍合成、棋子放置、棋盘障碍、溢出和棋盘暂存：

- **多倍合成**提高单次操作收益，但必须同时控制产出倍率、消耗和订单膨胀，否则会直接把原物品链打穿。
- **障碍与棋盘暂存**是空间压力的调节阀：太宽松，整理失去意义；太严格，玩家会被迫频繁付费或退出。
- **剧情三选一**提供轻量决策和情绪价值，但不能让选择结果与核心资源脱节。
- **通行证保留上次停留等级**，降低跨天回流成本；免费与付费奖励领完后，对应抽奖道具刚好消耗完，避免“领完还溢出一堆无效货币”。

### 3. 竞品、表现与协作

- 用模拟器、VPN、Google 账号、截图、录屏和视频剪辑拆竞品的美术、机制、奖励和交互。
- 用 Codex 做 AI 图像识别自动化脚本，辅助测试和素材检查。
- 拆入口 Icon、预告、开启、完成、主界面、玩法说明、礼包、Popup、Localization 和美术需求，与程序、美术、QA 对齐交付。

## 四、关键设计判断

### 为什么不能直接抄竞品？

竞品的界面只能说明“它现在有效”，不能说明你的用户、体力节奏、物品链和商业化能不能承接。真正要抄的是约束关系：

- 玩家一天能生成多少次；
- 从基础棋子到订单目标需要多少步；
- 棋盘能容纳多少个未完成分支；
- 订单需求偏向哪一阶物品；
- 阶段奖励在什么时候给，能否形成下一次操作动机。

这些参数一变，同一个 UI 会得到完全不同的体验。

### 棋盘空间为什么是核心资源？

二合的“难度”不只来自订单数值，也来自空间。低阶棋子积压会让玩家无法继续生成，形成隐性卡关。因此障碍、溢出和暂存不是附属功能，而是在调节：

**继续合成的机会 ↔ 整理棋盘的成本 ↔ 付费/等待的动机**

## 五、验证与结果

- 用 SVN / Unity + GM 覆盖活动开启、状态切换、数值配置、订单结算、奖励发放和异常场景。
- 按“控制流—配置—表现—异常”四层检查，避免只测正常路径。
- 对奖励发放、补发和领取状态进行核对，提交并跟进 Bug。
- 与程序、美术、QA 对齐入口、UI、本地化和配置字段，减少“文档写完但无法落地”的返工。

这里的成果是**系统实现与测试覆盖**，不等同于线上收入、留存或买量结果；上线数据属于团队结果，不作为个人战绩。

## 六、如果继续做，我会怎么验收

1. **首次体验：**首次合成、首次订单、首次棋盘满、首次阶段完成分别发生在第几分钟。
2. **节奏：**每日生成次数、订单完成时长、阶段完成天数和通行证进度是否与活动周期匹配。
3. **空间压力：**记录棋盘占用峰值、溢出次数、暂存使用率和因满盘退出率。
4. **随机偏差：**用固定种子和批量模拟检查连续不出目标物品的尾部情况，而不只看平均产出。
5. **商业边界：**付费是否能缩短等待，但不能直接跳过核心决策；免费玩家是否仍有完整的阶段目标。

## 七、可迁移的方法

- 把任何“合成/收集”玩法拆成生成、转换、需求、空间和奖励五个约束。
- 先跑最小闭环，再扩内容；先验证产出与需求是否闭合，再讨论美术和包装。
- 用状态机描述活动生命周期，用配置表描述可变内容，用日志验证实际到账。
- 不把竞品功能当立项理由，先回答“我们的用户为什么需要它、我们凭什么做得更好”。
