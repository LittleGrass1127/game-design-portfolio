# 数值设计方法｜从总消耗反推战斗与奖励

> 只写方法、流程和判断标准，不含项目内部 ID、原始配置和未公开内容。

## 1. 先定顶层目标

活动数值不从“怪物血量填多少”开始，而先定活动希望达成的总消耗、周期和成长上限，再把目标拆成：

- 活动天数与阶段；
- 玩家等级、技能和材料存量；
- 普通怪、Boss 和关卡难度；
- 商店限购、售价、升级材料；
- 局内奖励、阶段奖励、抽取和投放节奏。

## 2. 用有效生命和 DPS 反推怪物

把玩家属性折算成有效生命和 DPS，再匹配怪物的血量、攻击、攻速和技能。重点不是单个数值高低，而是：

- 同阶段玩家打同阶段怪是否成立；
- TTK 是否服务目标节奏；
- 玩家能吃几次技能、需要几次循环；
- 后期变强是来自等级，还是操作空间被压缩。

## 3. 技能平衡用乘区和覆盖率

多技能系统不能只比面板倍率。把技能拆成直伤、持续伤害、护盾、控制、增益和触发条件，再按乘区和覆盖率折算等效强度。

- 对叠层类效果设置上限，避免高叠层把后续内容打穿；
- 对新解锁技能按解锁顺序给递增系数，让玩家有换技能的理由；
- 对持续伤害单独处理施加、跳伤、减层和战斗结束截断，不把出手间隔当作跳伤间隔。

## 4. 用模拟扩大样本，用实机收口

- 固定阵容，覆盖不同养成阶段批量跑战斗；
- 看中位数和尾部，不只看平均值；
- 用 UE / GM 改资源、时间、解锁和任务状态，构造测试场景；
- 用 Lua 批量发奖、推进任务或循环造样本；
- 以服务器日志核对掉落、奖励到账和任务状态，请求发出不算成功。

## 5. 验收标准

- 首关可通关，相邻阶段没有难度断崖；
- 技能倍率逐档可解释，旧技能不跳关，新技能有使用理由；
- 商店产出和掉落产出不互相取代；
- 模拟参数、配置表、实机版本三者一致；
- 奖励入口不串包，任务、首杀和复刷按预期发放。
