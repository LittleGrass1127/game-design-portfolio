# 系统设计方法｜控制流、状态与异常

## 1. 活动系统：先定循环，再填模块

以 Merge 活动为例，先定义“玩—得—换—再玩”的闭环：

生成棋子 → 合成升级 → 完成订单 → 获得活动资源 → 推进阶段 → 领取奖励。

模块包括通行证、积分进度、无限奖励、进度条、剧情、图鉴、纪念物和 Reward。先定义活动控制流、订单积分与 Token 产出、结束结算和奖励补发，再补 UI、动效、Localization 和 Popup。

## 2. 差异不是换皮

- 在二合核心上增加棋盘操作和棋子溢出处理；
- 剧情做三选一，给玩家自主选择；
- 通行证保留上次停留等级，减少重复查找；
- 免费与付费奖励领完后，对应抽奖道具刚好消耗完。

## 3. 配置和前后端边界

配置表至少检查：活动时间、开关、积分阈值、奖励映射、字段 ID、引用关系和状态字段。

- 平衡和奖励核心字段：前后端同步；
- 纯展示 UI、图片和本地化字段：客户端保存；
- 奖励发放、结算和补发：服务端兜底；
- 异常场景：断线、重连、重复领取、结算后重算、奖励串包。

## 4. 用状态机写系统

以断线托管为例，把连接状态、角色生存状态和控制权分开记录：

正常在线 → 疑似断线 → 确认断线 → AI 托管 / 离线观战 → 重连交接 → 永久离开 / 已结算。

每次控制权交接递增版本号，拒绝旧客户端和重复交接；设置累计回控预算，防止反复断线滥用；重连同步位置、血量、背包、冷却和任务进度，同步完成前不改变控制者。

## 5. 验收

- 状态切换、数值配置、奖励发放和异常场景都能走通；
- 控制流、配置、表现、异常分层检查；
- 不把“正常路径走通”当成系统完成；
- 每个异常都有兜底、补偿或明确的失败提示。
