# 春风编花会 · 逆推策划文档

> 本文由原型代码（`prototypes/chunfeng.html` 拆分后的 `src/js/rules.js`）与仓库内作品说明逆推整理，数值均来自 `config/`。

## 1. 定位与设计问题

交互原型，只保留一个核心操作：**选花材 → 点击环形落点种植 / 拔除 → 看实时评价 → 提交花环**。作品说明中的定位是"花材布置与多目标评分"，四个原创交互原型的统一定位是"用于验证主操作链、界面信息和规则反馈"。

要验证的设计问题：

1. **多目标取舍**：色彩、株高层次、三位友邻的愿望分别指向不同花材，单种花材种满拿不到好评价。
2. **实时反馈是否足够引导**：右侧实时显示色彩和谐、高低层次、愿望命中数，玩家边种边看。
3. **无损重摆**：提交前可任意拔除重摆，未达标的提交不锁定、不损耗花材。

## 2. 核心循环

```
在种子篮选择花材（默认星铃花）→ 点击空落点种下 / 点击已种落点拔除
      → 实时看三项评价与愿望命中 → 种满 ≥12 株后「提交花环」
      → 达标：花环锁定，汇入公共花路
      → 未达标：指出是哪位友邻的愿望没满足，或者愿望全中但综合评分不够、差在哪一项
      → 「重新布置」清空全部落点（提交后也用它再来一环）
```

状态：`selected`（当前花材）、`slots`（16 个落点，存花材 id 或 null）、`submitted`（是否已通过提交）。

首屏引导：花坛标题下一句话写明目标（株数、愿望、通过线）和操作，数字从配置读取；右侧愿望列表里已满足的条目实时变色；花环锁定后再点落点会提示用「重新布置」。

## 3. 规则与数值公式

花材属性（`flowers.csv`）：

| 花材 | 颜色 | 株高 | 香型 |
| --- | --- | --- | --- |
| 星铃花 bell | 蓝 | 2 中株 | 2 清香 |
| 日光菊 sun | 黄 | 3 高株 | 1 淡香 |
| 风语草 wind | 绿 | 1 低株 | 3 浓香 |
| 霞光蔷薇 rose | 粉 | 2 中株 | 3 浓香 |

统计量：`planted` 已种株数、`colors` 颜色种数、`heights` 株高种数、`low` 株高 = 1 的株数、`fragrant` 香型 ≥ 3 的株数。

| 分项 | 公式 |
| --- | --- |
| 色彩和谐 harmony | `min(100, colors × 21 + min(planted, 12) × 2)` |
| 高低层次 layers | `min(100, heights × 25 + (low ≥ 2 ? 20 : 0))` |
| 愿望命中 wishes | `wishes.csv` 中满足 `统计量 ≥ min` 的条数（0–3） |
| 总分 total | `harmony × 0.42 + layers × 0.36 + wishes / 3 × 22`（满分恰为 100） |

愿望（`wishes.csv`）：阿柳 `colors ≥ 3`；团团 `low ≥ 2`；米米 `fragrant ≥ 2`。

提交：种植数 ≥ 12 且未提交时按钮可用；**三条愿望全中且 total ≥ 88** 才通过并锁定。未通过时保持可编辑，`submitVerdict` 返回原因：`missing`（列出未满足的愿望）或 `lowScore`（愿望全中但总分不够，反馈里给出当前的高低层次分）。

进度条：未提交 `planted / 12 × 82`%（种满 16 株时可到 109%，被进度条截断为 100%）；已提交 100%。

落点位置：第 i 个落点角度 `2π·i/16 − π/2`，半径为容器的 48%，从正上方顺时针排列。

### 数值观察（对 12–16 株的全部花材数量组合 3,480 种穷举，本次实际运行）

- 三愿望全中的组合 2,160 种，总分只有三档：83.74（只有低、中两种株高）、92.74（三种株高、三种颜色）、98.20（三种株高、四种颜色）。
- 通过线 88 把 83.74 这一档挡在外面：2,160 种里 335 种不通过，可通过 1,825 种；只种 12 株的 455 种组合里 210 种可通过。
- 例：12 株全星铃花，harmony 45、layers 25、wishes 0，总分 28，反馈列出三条未满足的愿望。
- 例：2 风语 + 5 星铃 + 5 蔷薇，三愿望全中，但没有高株，layers 70，总分 83.74，反馈提示补齐三种株高。
- 例：7 星铃 + 2 风语 + 1 日光 + 2 蔷薇，4 色 3 高，harmony 100、layers 95、wishes 3，总分 98，通过。

### 数值调整记录

| 项 | 原值 | 现值 | 原因 |
| --- | --- | --- | --- |
| `scoring.json` `pass.minTotal` | 72 | 88 | 三愿望全中时总分最低也有 83.74，原通过线 72 永远不会生效，提交是否通过完全由愿望决定，"高低层次"这项评价对结果没有影响。提到 88（落在 83.74 和 92.74 之间）后，愿望全中但缺高株的花环不通过，玩家需要再补一种株高。 |

## 4. 配置表说明

| 表 | 用途 | 字段 | 改了会影响 |
| --- | --- | --- | --- |
| `flowers.csv` | 花材池，种子篮按此生成 | `id` 唯一键；`name`（首字显示在落点上）；`color`；`height` 1–3；`scent` 1–3 | 花材卡、所有统计量与评分 |
| `attribute-levels.csv` | 等级显示名 | `attr`（height/scent）、`level`、`label` | 花材卡上的"中株 · 清香"等文字 |
| `wishes.csv` | 友邻愿望 | `id`；`npc`；`text` 文案；`stat` 引用统计量名（colors/heights/low/fragrant/planted）；`min` 门槛 | 右侧愿望列表、愿望命中、提交判定 |
| `scoring.json` | 系数 | `ring` 落点数、最少种植数、半径、默认花材；`stats` 低株 / 浓香判定线；`harmony`、`layers` 系数；`weights` 总分权重；`pass` 通过条件（是否要求愿望全中、通过线）；`progress` 进度条 | 花坛规模、全部分数、通过与否；首屏目标文案里的株数和通过线也读这里 |
| `texts.json` | 文案 | 花材卡模板、风向提示、愿望行模板、首屏目标（`{min}` `{pass}`）、三种提交反馈（通过 / 缺愿望 / 分数不够）、进度标签 | 界面文字 |

## 5. 验证方法

**本工程测试**：`node tests/config.test.cjs`，实际运行 84 条断言全部通过，覆盖：

- `config.generated.js` 与 `config/` 一致（等价 `export-config --check`）；
- 花材字段齐全、ID 唯一、株高 / 香型等级在 `attribute-levels.csv` 有定义、默认花材存在；
- 愿望 ID 唯一、`stat` 引用的统计量存在、门槛在 (0, 最少种植数]；花材池能满足颜色 / 低株 / 浓香愿望；
- 最少种植数 ≤ 落点数、比例权重在 (0,1)、三项满分时总分恰为 100、通过线在 (0,100]；
- 评分函数定值：空花坛、单色 12 株、混合方案；提交判定及未通过原因、拔除、提交按钮条件、落点坐标；
- 通过线起作用：愿望全中但只有两种株高的花环总分 83.74、不通过；穷举 3,480 种组合，愿望全中 2,160 种，其中 335 种被通过线挡下，可通过 1,825 种。

**浏览器对照**：用 headless Chromium 在拆分版和单文件版上执行同一套 31 步点击（种 12 株单色 → 提交，提示缺三条愿望 → 换花材补到愿望全中但缺高株 → 提交，提示分数不够 → 补一株高株 → 提交通过 → 锁定后点落点 → 重新布置），每一步比较页面文字、按钮状态、愿望勾选数、反馈样式、进度和评分环，结果一致，控制台无报错。

**已有验证**：作品说明只写明该原型用于验证主操作链、界面信息和规则反馈，没有试玩数据，此处不补充。

## 6. 已知限制

- 团团的愿望文案是"两株低矮**香花**"，规则只统计低株数量，不看香型；当前只有风语草是低株且恰为浓香，所以结果一致，新增低株花材时需注意。
- 规则只看花材数量，不看**相邻关系**：落点位置不影响评分，作品简介里的"相邻关系"在本原型中未实现。
- "今日风向：低株花材更容易保留香气层"只是提示文字，没有对应规则。
- 种植无库存限制；`style.css` 保留了原合集共用样式，未裁剪。
