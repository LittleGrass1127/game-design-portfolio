# 旧影回声 · 逆推策划文档

> 本文从 `prototypes/jiuying.html` 的代码逆推整理，数值与文案均以 `config/` 为准。

## 1. 定位与设计问题

四个原创交互原型之一（同组：夜灯街深夜剪辑室、春风编花会、精灵巡游季）。这组原型的定位是：“可离线运行的 HTML 原型，用于验证主操作链、界面信息和规则反馈”；对本原型的描述是“曝光修复、事实与推断分类、核对和整理”。

原型只回答一个问题：**在“修复照片”的调查玩法里，能不能让玩家自己分清“可直接核验的事实”和“需要关系判断的推断”，且出错时知道错在哪一步？** 题材是原创的“底片修复”调查情境（页面中的角色沈砚负责技术范围，玩家负责证据判断），不涉及数值成长或经济系统。

## 2. 核心操作链

```
调整曝光 → 进入可识别区间（出现日期/编号）
   → 选线索 → 归为事实 / 归为推断（两槽各一条）
   → 与沈砚核对（通过 / 不通过并提示原因）
   → 收录照片（发放一次性奖励）→ 「重新开始」回到初始状态
```

- 每一步都可回退：曝光可随时拖回、槽位可直接覆盖，“过度修复可以无成本回退，不会消耗提示次数”。
- 任何改动（拖曝光、重新归类）都会使已核对状态失效，必须重新核对。
- 同一条线索不能同时放在事实和推断两栏：放进一栏时，如果它已经在另一栏，另一栏清空。
- 收录后曝光、归类、核对都锁定，只能「重新开始」。
- 首屏引导：灯箱标题下一句话写明目标和四步操作，反馈条从"第一步：向右拖动曝光"开始，进入可识别区间后提示下一步去归类；右上角圆环显示修复进度。

## 3. 规则与反馈

| 规则 | 代码位置 | 说明 |
| --- | --- | --- |
| 曝光分区 | `rules.exposureZone` | `< readableMin` 偏暗；`[readableMin, readableMax]` 可识别；`> readableMax` 过曝 |
| 线索显影 | `ui/main.js render` | 仅可识别区间内 `--clue-opacity = 1`，底片上显示日期与编号 |
| 归类 | `rules.assignEvidence` | 把选中的线索放进一栏；同一条线索只能占一栏 |
| 核对按钮可用 | `render` | 事实槽与推断槽都已放入线索，且尚未收录 |
| 核对通过 | `rules.checkEvidence` | 曝光可识别 **且** 事实槽线索 `type=fact` **且** 推断槽线索 `type=inference` |
| 核对失败反馈 | `rules.checkFailReason` + `text.checkFailExposure / checkFailType` | 先看曝光：不在可识别区间就只提示调曝光；曝光对了才提示"有线索放错了栏"。不指明是哪一条 |
| 收录 | `render` | 仅核对通过且未收录时可点；奖励文案说明“同一底片重复修复不会重复发奖” |
| 重新开始 | `ui/main.js` | 状态回到 `createState()`，滑条、槽位、进度一并复位 |

线索与正确分类（`config/evidence.csv`）：

| 线索 | 类型 | 设计意图 |
| --- | --- | --- |
| 送洗单据（6 月 17 日） | 事实 | 有书面记录，可直接核验 |
| 相机编号（X-071） | 事实 | 机身记录，可直接核验 |
| 匿名留言（“不想让人认出”） | 推断 | 只能支持动机推断 |
| 划痕方向（与旧邮筒边缘相似） | 推断 | “相似”需要关系判断，是干扰项 |

## 4. 数值公式（取自代码）

- 灯箱亮度：`--exposure = visualBase + exposure / visualDivisor = 0.25 + exposure / 90`
- 曝光滑条：`min = 10, max = 100, initial = 30`；可识别区间 `52 ≤ exposure ≤ 76`（闭区间）
- 进度条（取已达到的最高阶段）：

| 阶段 | 条件 | 值 |
| --- | --- | --- |
| initial | 默认 | 12 |
| readable | 曝光在可识别区间 | 38 |
| classified | 两个槽位都已放入 | 62 |
| checked | 核对通过 | 82 |
| archived | 已收录 | 100 |

- 核对组合数：4 条线索 × 4 条线索 = 16 种槽位组合，其中正确组合 2 × 2 = 4 种（测试中穷举验证）。

## 5. 配置表说明

| 文件 | 字段 | 用途 / 改动影响 |
| --- | --- | --- |
| `evidence.csv` | `id, title, detail, slotName, type` | 右侧线索卡片由此生成；`type` 决定核对时的正确分类。增删行即增删卡片，改 `type` 会直接改变哪些组合能通过 |
| `evidence-types.csv` | `id, label, slotId, assignButtonId, placeholder` | 两个分类槽与“归为事实/推断”按钮的绑定、空槽占位文案。`id` 必须是 `fact` / `inference`（规则按此判定） |
| `exposure.json` | `min, max, initial, readableMin, readableMax, visualBase, visualDivisor` | 改可识别区间会改变操作难度（区间越窄越需要微调）；初始值应落在区间外，保证玩家有“调整”这一步 |
| `progress.json` | `initial, readable, classified, checked, archived` | 顶部进度条各阶段值，需单调递增，收录 = 100 |
| `text.csv` | `key, text` | 全部反馈文案；`progressLabel` 支持 `{step}` 占位 |

## 6. 验证方法

本工程测试（`node tests/config.test.cjs`，实际运行 **178 条断言全部通过**）：

- 导出一致性：`config.generated.js` 与 `render(loadConfig())` 逐字一致。
- 配置完整性：线索 ID 唯一、字段非空、`type` 引用的分类存在、每个分类至少一条线索、文案 key 唯一且代码引用的 key 全部存在。
- 数值范围：`min < readableMin ≤ readableMax < max`，初始曝光在范围内且不可识别；进度阶段 0–100 单调递增。
- 判定函数：曝光分区边界（51/52/76/77）；核对规则在 3 个曝光值 × 16 种组合上穷举，通过数 = 事实数 × 推断数；进度阶段逐级判定。
- 失败原因：曝光不对时一律报曝光，曝光对了才报分类；48 种组合上"无失败原因 ⇔ 核对通过"。
- 归类：同一条线索不能同时占两栏的四种情形。

拆分一致性：用 headless Chromium 对单文件版与拆分版执行同一组 24 步操作（把同一条线索先后放进两栏 → 放反并在偏暗时核对，提示调曝光 → 调到可识别再核对，提示放错栏 → 过曝再回调 → 换成正确线索 → 核对通过 → 收录 → 收录后再点归类 → 重新开始），每一步比较页面文字、按钮可用状态、反馈样式、进度宽度与圆环数值，结果一致，控制台无报错。

已有验证：作品说明写明这组原型“可离线运行”“用于验证主操作链、界面信息和规则反馈”，“全部页面使用原生 HTML、CSS 和 JavaScript，无需安装依赖”。除此之外没有可证实的用户测试记录，本文不作补充。

## 7. 已知限制

- 只有一张底片、4 条线索，无多案件、无提示次数系统（页面文案提到“不消耗提示次数”，但原型未实现提示功能）。
- 核对失败只区分"曝光"和"分类"两类原因，不指明是哪一条线索放错，属于有意保留的判断空间。
- `style.css` 为四个原型共用的样式表原样拆出，包含其它原型的主题变量（`data-game` 选择器），本页只用到 `jiuying` 主题。
