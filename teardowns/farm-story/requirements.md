> 说明：本文为参考经典农场游戏（星露谷物语）的复刻练习，部分角色与内容沿用原作设定，仅用于策划练习。

配套文档：[农场物语策划案](design.md)

## 0. 文档说明

### 0.1 编写目的

本文将《农场物语_策划案》中的产品设计和《农场物语_配置表》中的数值配置，整理为客户端、服务端/本地逻辑、UI、美术、音频和测试可以共同执行的实现需求。

本文只参考一份既有活动需求文档的需求粒度与组织方式，不引入其合成棋盘、活动 Token、纪念物或礼包玩法。

### 0.2 标记约定

| 标记 | 含义 | 研发处理方式 |
|-|-|-|
| `[已确定]` | 策划案或配置表已明确 | 按本文实现并纳入验收 |
| `[实现默认]` | 原资料未写明，为形成闭环而给出的默认方案 | 可先实现；评审若改动，以评审结论覆盖 |
| `[待确认]` | 原资料缺少关键规则或存在冲突 | 不得擅自固化为正式数值；在进入对应模块开发前确认 |

### 0.3 优先级

| 优先级 | 定义 | 主要范围 |
|-|-|-|
| P0 | 首个可玩闭环，必须实现 | 新建存档、时间、体力、耕种、收获、出售、睡觉、存档、基础 UI |
| P1 | 基础版本完整内容 | 养殖、采矿、战斗、钓鱼、觅食、烹饪、建筑、工具、社交、节日、收集 |
| P2 | 长线与运营内容 | 每日任务、签到、宝箱、赛季通行证、DLC 入口及相关联网能力 |

### 0.4 资料优先级

1. 已通过评审并回填的本文结论。
2. 数值取《农场物语_配置表》对应字段。
3. 玩法方向取《农场物语_策划案》。
4. 若同一规则冲突，进入本文第 14 章“待确认项”，不得由程序自行选择隐含规则。

# 1. 设计目的和产品概述

## 1.1 设计目的

- `[已确定]` 制作一款像素风农场经营与小镇社交模拟游戏。
- `[已确定]` 玩家继承爷爷的破旧农场，通过耕种、养殖、采矿、钓鱼、觅食、烹饪、建造和社交，使农场逐步繁荣。
- `[已确定]` 核心体验为治愈、成长、探索、归属和自由，不设置强制的单一路线。
- `[实现默认]` 主线目标只负责引导和解锁，不因玩家未完成而阻止日历自然推进。

## 1.2 核心循环

```Plaintext
起床
  → 查看日期、天气、日历和待办
  → 规划行动
  → 耕种 / 养殖 / 采矿 / 钓鱼 / 觅食 / 社交
  → 加工 / 烹饪 / 建造 / 升级
  → 出售产物并扩大生产
  → 回家睡觉
  → 当日结算与存档
  → 进入下一天
```

## 1.3 核心资源流向

| 资源 | 主要获取 | 主要消耗 | 是否持久化 |
|-|-|-|-|
| 金币 | 出售作物、动物产品、加工品、鱼、矿物和觅食物；任务奖励 | 种子、动物、工具升级、建筑、商品 | 是 |
| 体力 | 睡觉、食物、温泉、星落果提高上限 | 使用工具、耕地、浇水、钓鱼、采矿等 | 当前值和上限均持久化 |
| 生命 | 食物或其他恢复来源 | 矿井战斗受伤 | 是 |
| 原材料 | 砍树、采石、采矿、觅食、宝箱 | 建筑、升级、制作、烹饪 | 是 |
| 农产品 | 种植、养殖、加工 | 出售、烹饪、送礼、任务、收集 | 是 |
| 好感度 | 对话、送礼、任务 | `[待确认]` 是否存在衰减或负向行为 | 是 |
| 技能经验 | 对应玩法行为 | 不直接消耗，用于技能升级 | 是 |

## 1.4 产品边界

- `[已确定]` 俯视 2D 像素风，角色和场景精灵以 16×16 或 32×32 像素规格为基础。
- `[已确定]` UI 采用简洁木框风格，四季有独立主色和主题音乐。
- `[已确定]` 本体为买断制：PC 48 元，移动端 30 元；皮肤、宠物和扩展包可作为 DLC；不做影响核心数值的抽卡。
- `[实现默认]` P0、P1 按单机游戏设计；P2 运营功能单独接入账号、校时和订单校验，不反向阻塞离线核心玩法。
- `[待确认]` 配置表中的付费赛季通行证是否与买断制和“纯粹单机体验”的产品方向同时保留。

## 1.5 开发阶段

| 阶段 | 范围 | 完成门槛 |
|-|-|-|
| Phase 1 | 耕种、浇水、收获、出售、时间、睡觉、存档 | 完成 P0 验收；可连续游玩 7 个游戏日且存档一致 |
| Phase 2 | 养殖、采矿、战斗、钓鱼、觅食 | 各玩法形成获取、消耗、失败/退出和结算闭环 |
| Phase 3 | 社交、NPC 日程、好感事件、任务 | NPC 可稳定寻路；好感和事件不可重复错误触发 |
| Phase 4 | 节日、结婚、第二年内容、收集 | 跨季节、跨年、节日和婚后状态可正确保存 |
| Phase 5 | 平衡、性能、兼容、全量测试 | 完成第 13 章验收并关闭阻断级问题 |

> 原策划案为每阶段 1 周。本文保留阶段顺序，但具体工期应由研发根据资源量、地图量和待确认项重新评估。

# 2. 全局游戏流程

## 2.1 游戏状态机

```Plaintext
标题界面
  ├─ 新游戏 → 创建存档 → 开场剧情 → 当日游戏
  └─ 继续游戏 → 读取存档 → 当日游戏

当日游戏
  ├─ 暂停菜单 / 普通功能界面 → 返回当日游戏
  ├─ 对话 / 剧情 / 节日 → 结束后返回当日游戏
  ├─ 生命归零 → 战斗失败结算 → 返回安全地点
  ├─ 02:00 到达 → 晕倒结算
  └─ 主动睡觉 → 当日结算

当日结算
  → 出售结算
  → 作物、动物、建筑、任务、Buff 等跨日结算
  → 原子存档
  → 日期推进
  → 次日 06:00 起床
```

## 2.2 新建存档

### 输入

- `[实现默认]` 角色名称、外观、农场名称、宠物偏好和存档槽位。
- `[待确认]` 农场地图类型、难度选项、初始资金、初始工具和开场剧情具体内容。

### 结果

- 创建唯一 `save_id`。
- 初始化日期为第 1 年春季第 1 天 06:00。
- 初始化最大体力为 270。
- 初始化玩家、农场、背包、图鉴、任务、NPC、世界和版本数据。
- 若创建过程失败，不生成半成品存档；返回标题界面并提示重试。

## 2.3 当日开始

系统按下列顺序执行：

1. 读取并校验存档版本。
2. 应用上日结算结果。
3. 设置时间为 06:00。
4. 刷新天气、NPC 日程、地图采集物、动物状态和每日任务。
5. 处理建筑施工剩余天数、邮件、节日和剧情触发。
6. 弹出当日必要通知；多个弹窗按“阻断剧情 → 系统解锁 → 奖励 → 普通提示”排序。
7. 玩家获得控制权。

## 2.4 时间、日期和季节

| 参数 | 规则 |
|-|-|
| 起床时间 | `[已确定]` 06:00 |
| 最晚时间 | `[已确定]` 02:00，达到后强制晕倒 |
| 每小时 | `[已确定]` 约 43 秒现实时间 |
| 每季 | `[已确定]` 28 天 |
| 每年 | `[已确定]` 112 天，顺序为春、夏、秋、冬 |
| 暂停/加速 | `[已确定]` 支持暂停和加速；`[待确认]` 可用倍率和可使用场景 |

### 日期换算

```Plaintext
year = floor((absolute_day - 1) / 112) + 1
day_in_year = ((absolute_day - 1) mod 112) + 1

1～28   = 春
29～56  = 夏
57～84  = 秋
85～112 = 冬
day_in_season = ((day_in_year - 1) mod 28) + 1
```

### 时间推进默认规则

- `[实现默认]` 普通探索和操作时推进游戏时间。
- `[实现默认]` 暂停菜单、背包、设置、教程、完整剧情和节日结算时暂停游戏时间。
- `[实现默认]` 对话、商店、钓鱼小游戏是否暂停由统一 `TimePausePolicy` 配置，P0 默认暂停。
- `[实现默认]` 移动端进入后台时立即暂停并写入安全检查点。
- `[待确认]` “一天约 13 分钟”与“每小时约 43 秒”不完全一致。当前实现以更具体的 43 秒/小时为准，从 06:00 到次日 02:00 约 14 分 20 秒。

## 2.5 天气

- `[已确定]` 春季多雨、夏季以晴天为主、秋季多风、冬季多雪。
- 天气至少支持：晴、雨、风、雪。
- 雨天应影响农田浇水；雪天、风天的其他数值效果均为 `[待确认]`。
- `[实现默认]` 在前一日结算时生成次日天气，并保存结果；读取存档不得重新随机。
- 节日或剧情需要固定天气时，固定配置优先于随机天气。
- `[待确认]` 各季天气权重、连续天气保护、雷暴等特殊天气及天气预报范围。

## 2.6 睡觉、晕倒与跨日结算

### 主动睡觉

1. 玩家与床交互。
2. 弹出“是否结束今天”确认。
3. 确认后锁定输入，进入结算；取消则返回游戏。
4. 结算成功后保存并进入下一天。

### 02:00 晕倒

- 时间到达 02:00 后立即停止普通输入并触发晕倒。
- `[待确认]` 晕倒后的金币扣除、物品丢失、次日体力惩罚和醒来地点。
- 未确认惩罚前，P0 默认只强制结束当天，不扣金币和物品，并记录一次 `faint_reason=time_limit`。

### 跨日结算顺序

1. 冻结当日输入和奖励请求。
2. 结算出货箱与当日收入。
3. 结算 Buff 到期和临时状态。
4. 结算已浇水作物的生长、重复收获倒计时和季节切换。
5. 结算动物年龄、喂食、好感和产品计时。
6. 结算建筑施工和工具升级剩余天数。
7. 结算任务到期、节日状态和 NPC 日程。
8. 推进日期，生成次日天气及日常内容。
9. 恢复体力至最大值。
10. 写入完整存档；成功后才显示次日起床画面。

# 3. 存档与数据一致性

## 3.1 存档内容

| 数据域 | 最低保存内容 |
|-|-|
| 元数据 | `save_id`、存档版本、创建时间、最后保存时间、平台、游戏版本 |
| 玩家 | 位置、朝向、金币、体力、生命、技能、装备、工具、外观 |
| 时间 | 年、季、日、时刻、当日天气、次日天气、随机种子 |
| 背包/仓库 | 物品 ID、数量、品质、耐久/实例属性、所在容器 |
| 农场 | 地块状态、作物实例、建筑、装饰、障碍物、动物 |
| 世界 | 地图采集物、矿井进度、宝箱、节日、已触发剧情 |
| 社交 | NPC 好感、每日对话/送礼标记、事件、恋爱、婚姻、生日状态 |
| 收集 | 出货、鱼类、矿物、料理和博物馆图鉴状态 |
| 任务 | 主线、支线、每日任务进度、领取状态、刷新批次 |
| 运营 | 签到周期、赛季 ID/经验/等级、免费和付费奖励领取位图、交易凭证 |

## 3.2 保存时机

- `[已确定]` 正式跨日存档发生在睡觉结算后。
- `[实现默认]` 新建存档完成、重要剧情结束、进入后台、付费成功和领取唯一奖励后写入安全检查点。
- 安全检查点不推进日期，不重复结算当日出货或作物成长。

## 3.3 原子性与恢复

- 保存采用“写临时文件 → 完整性校验 → 替换主存档”的原子流程。
- 每个存档至少保留上一版可读备份。
- 存档包含校验值；损坏时先尝试备份，仍失败则停止加载并提示，不创建空白覆盖原文件。
- 领取奖励、购买、结婚、星落果等不可逆操作必须带唯一事务 ID，重复请求只返回首次结果。
- 随机结果在结算前写入事务或保存随机种子，读档不得通过反复重试改变已结算奖励。

## 3.4 版本迁移

- 配置 ID 持久化后不得直接复用为另一物品。
- 删除配置前必须提供旧 ID 的迁移或废弃映射。
- 迁移失败时保留原始存档并记录失败字段，禁止静默丢弃玩家资产。

# 4. 通用规则

## 4.1 输入与交互

- PC 支持键鼠和手柄；移动端支持虚拟摇杆/点触。
- 所有玩法调用统一动作：移动、主交互、使用工具、次交互、打开背包、取消。
- `[实现默认]` 同一帧只提交一次会消耗资源的动作，避免连点重复扣除。
- 目标超出距离、被阻挡、资源不足或容器已满时，动作失败且不得扣体力、金币或物品。
- `[待确认]` 具体按键、手柄映射、触屏操作方案、自动寻路和辅助瞄准。

## 4.2 背包与物品

- 物品实例至少包含 `item_id`、数量、品质和可选实例属性。
- 配置表 `ItemConfig` 决定物品类型、售价、可食、恢复量和增益。
- 物品进入背包前先检查合法 ID 和容量；失败时保持原世界物品，不得直接销毁。
- 任务、奖励和宝箱发放时，若背包不足，进入待领取容器或邮件；`[待确认]` 具体承载系统。
- `[待确认]` 背包初始格数、扩容、单格堆叠上限、物品丢弃和拆分规则。

## 4.3 金币与售价

```Plaintext
单项售价 = 配置中该物品/品质的售价 × 数量
总收入 = 所有有效出售项售价之和
```

- 金币使用非负整数保存；计算过程使用至少 64 位整数。
- 购买先完整校验金币、前置、容量和商品状态，再一次性扣款并发货。
- 售价直接读取配置，不由客户端根据显示价格反推。
- 作物不同品质售价读取 `CropConfig` 的普通、银星、金星、铱星字段。
- `[实现默认]` 出货箱物品在睡觉后一次性结算；结算前可取回，确认睡觉后不可修改。
- `[待确认]` 商店是否允许即时出售，以及加工品、动物产品、鱼类银星售价等缺失值。

## 4.4 体力和生命

| 规则 | 实现要求 |
|-|-|
| 初始最大体力 | `[已确定]` 270 |
| 星落果 | `[已确定]` 每个永久增加 34 上限，可叠加 |
| 恢复 | `[已确定]` 睡觉恢复至满；食物和温泉可恢复 |
| 工具消耗 | `[已确定]` 单次约 2～4；具体动作表 `[待确认]` |
| 下限/上限 | `[实现默认]` 当前体力限制在 `0～max_energy` |

- 使用工具前检查体力；不足时动作不生效、不扣除体力。
- 食物的体力和生命恢复分别计算并封顶，不允许超过上限。
- `I010 树液`配置为可食且体力 -2，使用后体力最低为 0。
- 生命归零只触发战斗失败，不等同于 02:00 晕倒。
- `[待确认]` 初始/最大生命、温泉恢复速度、体力为 0 的表现、战斗失败惩罚。

## 4.5 Buff

- Buff 由 `BuffConfig` 定义属性、数值、持续时长和叠加规则。
- B001～B007 持续 420 游戏分钟且不可叠加；再次获得同 ID Buff 时，`[实现默认]` 数值不叠加、持续时间刷新为 420 分钟。
- B008 `MAX_EN+34` 为永久且可叠加，写入永久体力上限，不作为临时 Buff 倒计时。
- 暂停游戏时 Buff 的游戏内时长不减少；睡觉跨日时按跨过的游戏时间或清除规则处理，具体为 `[待确认]`。
- UI 显示 Buff 图标、剩余游戏分钟和数值；永久效果不显示倒计时。

# 5. 核心玩法功能逻辑

## 5.1 耕种系统（P0）

### 5.1.1 基本流程

```Plaintext
可耕地
  → 使用锄头翻地
  → 选择合法种子播种
  → 每日浇水
  → 满足生长天数
  → 成熟
  → 收获并进入背包
  → 一次性作物清除 / 重复作物进入再生倒计时
```

### 5.1.2 地块状态

| 状态 | 可执行操作 | 结果 |
|-|-|-|
| 不可耕 | 清障或无操作 | 未满足条件时不能翻地 |
| 可耕未翻 | 锄地 | 变为已翻干地，扣除对应体力 |
| 已翻干地 | 播种、浇水、复原 | 可进入已播种或湿润状态 |
| 已翻湿地 | 播种 | 当天保持已浇水标记 |
| 已播种未成熟 | 浇水 | 设置当日已浇水；夜间满足条件则生长 |
| 已成熟 | 收获 | 发放产物；根据作物类型清除或进入再生 |
| 枯萎/失效 | 清除 | 清除后保留或移除耕地状态，规则待确认 |

### 5.1.3 播种校验

同时满足以下条件才允许播种：

1. 目标为允许种植的已翻地块。
2. 地块无其他作物、建筑、动物或阻挡物。
3. 背包中存在对应种子。
4. 当前季节包含在 `CropConfig.季节` 中，或地块位于允许全年种植的温室。
5. 配置 ID 存在且未被禁用。

任一条件失败均不消耗种子。

### 5.1.4 生长计算

- `生长天数`表示完成成熟所需的有效生长结算次数。
- `[实现默认]` 播种当天记为第 0 天；每次跨日时，若当天已浇水，则有效生长天数 +1。
- 达到配置生长天数后，次日 06:00 显示为成熟。例如春 1 日播种生长 4 天的防风草，并连续浇水，于春 5 日可收获。
- 未浇水当天不增加有效生长天数，作物不倒退。
- 雨天自动将露天地块标记为已浇水；温室是否自动受天气影响为否。
- 肥料应在地块数据中预留 `fertilizer_id`，但肥料种类、持续时间和效果为 `[待确认]`。

### 5.1.5 收获与再生

- 一次性作物收获后移除作物实例，耕地保留。
- 重复作物首次成熟后，收获时设置 `regrow_remaining_days = 重复间隔`；每次有效跨日结算减 1，为 0 时再次成熟。
- 蓝莓每次基础产出 3 个；蔓越莓每次基础产出 2 个；土豆每次有 20% 概率额外 +1；其他作物默认 1 个。
- 随机额外产出必须在一次收获事务中结算，重复点击不得多次获得。
- 背包空间不足时不移除成熟状态；成功放入全部产物后才完成收获。
- `[待确认]` 多个产物是否共用品质、作物品质概率、肥料和技能对品质的影响。

### 5.1.6 季节切换

- 跨季作物仅在配置允许的季节继续生长，例如玉米允许夏、秋，上古水果允许春、夏、秋。
- `[实现默认]` 不支持新季节的露天作物在换季结算时变为枯萎；温室内不受季节限制。
- 冬季种子、温室解锁和社区中心规则未在配置表完整定义，进入对应内容制作前必须补齐。

### 5.1.8 异常与边界

- 对同一地块快速连点：只接受第一笔有效事务。
- 动画未结束切换场景：以逻辑结算结果为准，重进后恢复最终状态。
- 配置不存在：阻止播种/收获并记录错误，不删除种子或作物实例。
- 跨季、睡觉、崩溃恢复同时发生：跨日结算只能提交一次。
- 时间到 02:00 时正在收获：已提交成功的收获保留；未提交动作取消。

## 5.5 钓鱼系统（P1）

### 5.5.1 流程状态机

```Plaintext
持有鱼竿并面向水面
  → 抛竿蓄力
  → 浮漂落在合法水域
  → 等待咬钩
  → 提示窗口内拉钩
  → 钓鱼小游戏
  ├─ 成功：按地点、季节、天气、时间抽取鱼并结算品质
  └─ 失败：不获得鱼
```

### 5.5.2 候选鱼过滤

候选鱼必须同时满足：

1. 当前地图/水域匹配 `FishConfig.地点`。
2. 当前季节包含在配置季节中。
3. 当前天气符合配置，`任意`表示不限制。
4. 当前游戏时间处于配置时间窗。
5. 特殊前置、鱼竿、技能等条件满足。

跨午夜时间窗按以下方式判断：

```Plaintext
若 start <= end：start <= now < end
若 start > end：now >= start 或 now < end
```

例如 `18-02` 覆盖 18:00 至次日 02:00，不包含 02:00 强制晕倒时刻。

### 5.5.3 小游戏与结算

- 鱼类难度和行为读取 `FishConfig.难度/行为`；行为至少支持平稳、混合、下沉。
- 抛竿、等待、咬钩、拉钩和结果阶段不可重复提交。
- 成功后抽取一条候选鱼并确定品质；背包满时结果保留在临时收获槽，玩家处理后才能继续抛竿。
- 鱼的普通、金星、铱星售价读取配置。
- `[待确认]` 咬钩概率、小游戏具体公式、钓鱼条尺寸、失败阈值、银星鱼售价/是否存在银星、鱼尺寸和宝箱规则。

### 5.5.4 特殊鱼

- 传说之鱼 F008：山区湖、春季、雨天、06:00～20:00、难度 110。
- `[实现默认]` 传说之鱼作为唯一收集物，每个存档最多成功获得一次；该规则须在评审确认后进入正式配置。

# 6. 任务、签到、宝箱与赛季（P2）

> 本章来源于《农场物语_配置表》，但策划案将产品定位为买断制单机游戏。是否上线本章功能必须先完成商业化和计时方式评审。未完成评审时，本章不得成为 P0/P1 的登录阻断项。

`[实现默认]` 在评审完成前，`DailyQuest`、`DailyLogin`、`Chest`、`SeasonPass`四个功能开关均为关闭；关闭时不显示入口、不刷新数据，也不影响旧存档中的核心资产。

## 6.1 每日任务

### 6.1.1 刷新

- `[已确定]` 每天 06:00 从权重池抽取 3 个任务，未完成任务不累计。
- `[实现默认]` “每天”指每个游戏日，不读取设备自然日。
- 先过滤未开启、配置无效和当前存档绝对无法完成的任务，再按权重无放回抽取。
- 随机种子由 `save_id + absolute_day + quest_pool_version`确定；同一天读档结果不变。
- 有效候选少于 3 个时只发放有效数量并记录配置警告，不使用无效任务补足。

### 6.1.2 进度与领取

- 任务实例保存 `quest_id`、目标快照、当前进度、完成状态、领取状态和刷新批次。
- 进度只监听任务生成后的合法行为事件，生成前的行为不追溯。
- 进度达到目标时封顶，不因出售退款、读档等重复回调二次累计。
- `[实现默认]` 奖励手动领取；已完成但刷新前未领取的奖励进入待领取容器，避免丢失。
- `[待确认]` `奖励经验`属于技能经验、玩家经验还是赛季经验。

### 6.1.3 任务事件映射

| 目标类型 | 事件 | 计数口径 |
|-|-|-|
| 收获 | `crop_harvest_committed` | 按实际进入背包的作物数量 |
| 出售 | `item_sale_committed` | 按结算成功数量或单笔价值条件 |
| 浇水 | `tile_watered` | 同一地块同一天首次有效浇水 |
| 采集 | `item_gathered` | 按来源和目标物品 ID 过滤 |
| 钓鱼 | `fish_caught` | 成功结算的鱼数量 |
| 送礼 | `gift_committed` | 成功交付给 NPC 的礼物次数 |
| 互动 | `animal_petted` | 同一动物同一天首次抚摸 |
| 制作 | `recipe_crafted` | 成功制作数量 |
| 清除 | `obstacle_removed` | 指定障碍被完整清除 |
| 开箱 | `chest_open_committed` | 宝箱事务成功次数 |

## 6.2 宝箱

### 6.2.1 开箱事务

1. 校验宝箱实例、来源、所有权和未开启状态。
2. 根据 `chest_type`读取最小/最大掉落项数。
3. 使用持久化随机种子生成掉落，不因重复点击或读档重抽。
4. 生成完整奖励预览并预留背包/待领取空间。
5. 一次性写入“已开启”和全部奖励。
6. 播放开箱与奖励展示；表现中断不影响已提交结果。

### 6.2.2 掉落算法实现默认

```Plaintext
N = RandomInt(min_item_count, max_item_count)
G = 当前掉落池中 guaranteed=true 的有效条目集合
M = min(N, count(G))

先从 G 按权重无放回抽取 M 项；
再从尚未被抽中的全部有效条目中按权重无放回抽取 N-M 项；
每项数量在 [min_count, max_count] 中独立随机；
金币直接入账，其他物品进入背包或待领取容器。
```

- 同一掉落行在单箱内不可重复选中。
- 若 N 大于有效独立条目数，运行时将 N 收缩为有效条目数并上报配置错误；正式发布前配置检查必须阻止此情况。
- `ChestInstanceConfig.pool_id`应改为掉落池组 ID，不使用 `P010-P014` 形式的字符串范围作为外键。
- 开箱请求使用 `chest_uid`幂等，同一实例只能成功一次。

### 6.2.3 已知阻断

- 原算法中的 M 未定义；本文给出的 M 规则需评审确认。
- MYSTERY 最大 5 项但仅 4 个池条目，SEASONAL 最大 4 项但仅 3 个池条目，与无放回冲突。
- 随机赛季物品、赛季装饰和种子包没有实际候选配置。
- 可重复宝箱含永久叠加的星落果，可能使体力上限无限增长；应设置存档总上限、改为唯一奖励或从重复池移除。
- 唯一宠物、皮肤、称号重复获得后的替代奖励未定义。

## 6.3 每日签到

- `[已确定]` 7 天一轮：第 1 天 100 金币，第 2 天木材×20，第 3 天南瓜汤×1，第 4 天 200 金币，第 5 天木宝箱，第 6 天石材×20，第 7 天银宝箱；之后回到第 1 天。
- 每次领取保存唯一 `login_cycle_id + day_index`，重复请求不得再次发放。
- 背包不足时物品奖励进入待领取容器，金币直接入账。
- `[待确认]` 以现实日还是游戏日刷新、刷新时区、漏签、补签、连续签到翻倍触发条件和是否自动领取。
- 未确定计时来源前，不得使用设备本地时间直接判定，以免修改系统时间重复领取。
- `CHEST_RAND_02`当前描述为节日银宝箱，复用于签到前应改为通用银宝箱实例或修正文案。

## 6.4 赛季通行证

### 6.4.1 生命周期

```Plaintext
未开始 → 进行中 → 结束待结算 → 已关闭
```

- 进行中才可获得赛季经验、购买付费轨和领取奖励。
- 免费奖励按等级解锁；付费奖励同时要求达到等级且已拥有付费权限。
- 后购买付费轨时，可追溯领取此前已达到等级的付费奖励。
- 每个奖励节点保存独立领取位，重复请求幂等。
- 赛季结束时，已达成未领取奖励的处理为 `[待确认]`；实现默认进入待领取容器。

### 6.4.2 当前配置解释

- S1～S4 分别为 Day1～112、113～224、225～336、337～448。
- `[实现默认]` `Day`解释为存档的绝对游戏日，而非现实日期；若改为现实赛季，必须替换为服务器时间戳。
- `30 / 98`无法确定是货币、双档价格还是平台价格，购买功能在字段拆分前禁用。
- 配置声明免费 50 级、付费 80 级，但奖励最高只到 50 级；51～80 级内容缺失。
- S2～S4 奖励明显不完整，不能用于正式发布。

### 6.4.3 升级和奖励

- 需新增 `SeasonLevelConfig`，至少包含 `season_id`、等级、累计经验、升至下级经验。
- 需明确赛季经验来源、每日/每周上限、溢出经验和满级行为。
- `SeasonRewardConfig`中的种子奖励不应直接使用作物 ID，需使用独立种子 Item ID。
- `RECIPE`、`DECO`、`PET`、`SKIN`、`MOUNT`、`TITLE`奖励必须分别存在有效配置和重复获得转换规则。
- 付费轨包含铁矿石、钻石等数值资源，与“外观 DLC 不影响数值”方向冲突，商业化评审前不得上线。

## 7.4 耕种表现

- 锄地：工具挥动 → 命中格反馈 → 地块材质切换 → 体力栏变化。

- 浇水：水流覆盖合法格 → 湿润材质切换；范围浇水按固定顺序播放，但逻辑一次提交。
- 生长：跨日起床时直接读取新阶段；首次进入农场可播放低强度生长提示，不逐格阻断。
- 收获：作物缩放/弹起 → 物品飞向玩家/背包 → 数量和任务进度更新。
- 背包满时不播放“飞入背包完成”表现，作物保持成熟。


- 普通奖励可点击任意空白区域关闭；包含选择、付费或不可逆确认的弹窗不得用空白点击关闭。

# 8. 配置需求

## 8.1 配置加载原则

- 配置是玩法数值的唯一来源；逻辑层不重复硬编码价格、天数、奖励和权重。
- 所有表必须声明主键、字段类型、默认值、空值含义、单位、枚举和外键。
- 开发/测试包启动时执行全量配置校验；正式配置进入资源管线前执行同一校验。
- 配置版本写入存档。热更新后若会改变已存在实例的解释，必须提供迁移策略。
- 表格文本统一使用 UTF-8；ID、枚举、路径和多语言 Key 使用半角字符。

## 8.3 字段标准化

### 8.3.1 通用元信息

每张配置建议保留四类说明行或等价 Schema：

```Plaintext
var   = 字段名
type  = int / int64 / float / bool / string / enum / array / struct
group = 客户端、服务端、共享或编辑器分组
desc  = 中文说明、单位、枚举、空值和边界
```

### 8.3.2 禁止使用不可解析文本承载结构数据

| 当前写法 | 问题 | 目标结构 |
|-|-|-|
| `木300+石100` | 名称不稳定，无法外键校验 | `materials:[{item_id:I001,count:300},{item_id:I002,count:100}]` |
| `铜锭×5` | 铜锭尚无 Item ID | `material_item_id + material_count` |
| `夏秋`、`春夏秋` | 自由文本易产生解析分支 | `seasons:[SUMMER,AUTUMN]` |
| `18-02`、`全天` | 时间格式不统一 | `start_minute`、`end_minute`、`all_day` |
| `P010-P014` | 范围字符串不是外键 | `drop_group_id`关联多条池数据 |
| `30 / 98` | 无法确定含义 | `price_tier_1`、`price_tier_2`、`currency`或独立商品表 |
| Item 的 `增益=DEF+2` | 名称字符串不是稳定外键 | `buff_id=B002` |
| 任务目标数量 0 表示价值 | 同字段多义 | `target_count`与`target_conditions`分离 |

## 8.5 发布前自动校验

### 阻断发布

- 主键为空或重复。
- 字段类型、枚举、时间或数组无法解析。
- 任何正式启用行存在无效外键。
- 金币、数量、天数、间隔、权重出现非法负值；允许负值的字段必须显式声明。
- `min > max`、掉落数量大于无放回池容量、有效任务候选少于设计最低数量。
- 建筑前置形成循环，或工具升级链跳级/重复。
- 赛季日期重叠、开始不小于结束、奖励等级超过等级配置。
- 必要资产或多语言 Key 缺失。

### 行级禁用并报警

- 非核心 P2 任务自身数据错误，但禁用后仍有足够合法候选。
- 可选 NPC 礼物偏好中的单个物品不存在。
- 未启用赛季的奖励不完整。

### 警告

- 售价为 0、奖励为空、权重为 0、描述与结构字段不一致。
- 同类数值异常偏离，例如付费奖励投放永久成长物或高阶资源。
- 可重复来源包含唯一/永久奖励但未配置重复转换或总上限。

# 10. 技术与非功能需求

## 10.1 确定性与事件系统

- 时间、天气、掉落、任务、宝箱和跨日结算使用可保存的确定性随机源。
- 各系统通过已提交的领域事件更新任务、图鉴和技能，不直接监听按钮点击。
- 关键事件至少包含唯一事件 ID、存档 ID、游戏日、来源、目标、数量和提交结果。
- 同一事件重复投递时，任务、图鉴、奖励和经验只能处理一次。

## 10.2 性能

- `[实现默认]` 目标平台正常场景以 60 FPS 为目标，低规格设备最低可玩线为稳定 30 FPS；正式机型清单待确认。
- 大地图对象使用视野裁剪、分区加载和对象池；离屏作物、动物和 NPC 不持续运行完整逐帧逻辑。
- 跨日结算按批处理执行，不能因数百地块逐个播放或逐个写盘而长时间卡死。
- `[实现默认]` 普通场景切换目标不超过 3 秒、跨日保存目标不超过 2 秒；需在指定最低设备和标准存档规模上复测后定稿。
- 存档规模、农场最大地块、最大动物数和最大装饰数为 `[待确认]`，确定后必须加入压力测试。

## 10.3 平台与适配

- UI 支持常用移动端长宽比、安全区、刘海和横竖屏策略；`[待确认]` 游戏采用横屏或竖屏。
- PC 支持窗口、无边框和全屏，分辨率变化不丢失按钮和关键信息。
- 手柄焦点不能进入不可见控件；所有弹窗都有明确默认焦点。
- 存档路径、云存档、跨平台同步和存档槽数量为 `[待确认]`。

## 10.4 可访问性

- 重要状态不只依赖颜色；成熟、可领取、危险和禁用状态同时使用图标/文字。
- 支持 UI 缩放、字幕、震动开关、闪烁强度降低和按键重映射；具体支持范围评审确认。
- 钓鱼小游戏应预留难度辅助参数，不改变基础掉落表。

## 10.5 P2 联网与付费安全

- 付费、现实时间赛季和签到若上线，以可信服务器时间及账号资产为准。
- 客户端不得自行确认支付成功；使用平台订单号幂等发货。
- 断网不影响 P0/P1 核心单机存档；P2 入口展示离线状态并允许稍后重试。
- 日志和分析数据不得包含玩家输入的敏感信息或完整支付凭证。

## 12.3 事务约束

- 每个消耗/奖励接口接收 `transaction_id`，返回成功、可重试失败或永久失败。
- 只有成功提交后才发布领域事件；UI 点击、动画开始和预览不发布结算事件。
- 同一事务重复调用返回首次结果，不重新随机、不重复扣除、不重复发奖。
- 复合操作必须全部成功或全部回滚，例如购买动物包含扣金币、创建动物和写入建筑。
- 跨日结算由单一编排器调用各模块，模块不得自行推进日期。

# 13. 验收标准

## 13.1 通用格式

每个用例至少记录：前置存档、配置版本、固定随机种子、操作、预期数据、预期表现和重进后的最终状态。标记为 `[待确认]` 的规则在确认前不作为数值验收依据，但相关结构和安全边界仍须验证。

## 13.2 核心流程与存档

| 编号 | 前置条件与操作 | 预期结果 |
|-|-|-|
| TIME-001 | 春 1 日 06:00 进入世界，分别在普通场景和暂停菜单观察时钟 | 普通场景按最终倍率推进；暂停期间不推进 |
| TIME-002 | 将时间推进到 02:00，并在晕倒表现中杀进程后重进 | 只结算和推进一天，不重复扣除或发放 |
| TIME-003 | 分别从春 28、夏 28、秋 28、冬 28 睡觉 | 正确进入下一季；冬 28 后进入下一年春 1 |
